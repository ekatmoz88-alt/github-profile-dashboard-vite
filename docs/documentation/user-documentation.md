# User & Administrator Documentation

## Purpose

User documentation helps people complete tasks safely and correctly. Its structure should reflect real workflows, user roles, and the system's implemented behavior.

## Document types

- **User guide:** tasks, workflows, interface elements, expected results.
- **Operator guide:** routine operations, monitoring, recovery, and operational checks.
- **Administrator guide:** installation, configuration, access management, maintenance, and troubleshooting.
- **Quick reference:** concise task or command lookup.
- **Troubleshooting guide:** symptoms, diagnostic steps, causes supported by evidence, and resolution paths.

## Task-oriented procedure structure

A procedure should normally include:

1. Purpose and when to use it.
2. Required role, permissions, and prerequisites.
3. Initial state or required input.
4. Numbered actions in the order performed.
5. Expected result and confirmation.
6. Exceptions, warnings, and recovery steps.

Use one action per step where practical. Name interface controls exactly as they appear. Explain outcomes rather than merely repeating button labels.

## Screenshots and examples

Use screenshots when they clarify a visual task or state. Keep them current, readable, and free of sensitive information. Captions should explain what the image demonstrates. Examples must match actual system behavior and must not expose personal or production data.

## Accuracy

Document only workflows supported by specifications, source artifacts, observed behavior, or subject matter expert confirmation. Distinguish role permissions and environment-specific behavior. Do not turn assumptions into instructions.

## Review checklist

- Is the audience and task clear?
- Are prerequisites and permissions stated?
- Are steps complete and correctly ordered?
- Is the expected result observable?
- Are warnings and recovery paths accurate?
- Do screenshots and labels match the current interface?
- Are version and environment differences identified?
