# Project Evidence & Case-Study Structure

## Purpose

This document defines how portfolio case studies connect project claims to real artifacts. It complements, and does not replace, the [Documentation Quality Assurance](documentation-quality-assurance.md) model for technical evidence, claim traceability, and verification.

## Case-study structure

1. **Project context** — system purpose, audience, scope, and technical environment.
2. **Documentation challenge** — the information or documentation problem addressed.
3. **Reference basis** — applicable standards, specifications, and professional references.
4. **Applied methodology** — analysis, information architecture, authoring, and verification activities.
5. **Documentation artifacts** — actual documents, source files, specifications, diagrams, and published materials.
6. **Verification** — checks performed and evidence available; state the actual scope and result.
7. **Outcome** — completed deliverables and demonstrable improvements.

## Portfolio evidence practices

- Link to the actual artifact whenever it can be published.
- Identify source version or extraction context when relevant.
- State limitations and unavailable verification.
- Keep evidence attached to the project and subsystem it actually describes.
- Do not publish confidential documents, personal data, credentials, or production records.
- Do not claim quantified business impact without supporting measurements.

Similar technologies or shared integration points do not justify merging separate project contexts. Preserve the actual boundaries between projects, products, and subsystems.

## Outcome claims

Describe completed work and deliverables directly. Claims about performance improvements, reduced support workload, adoption, or business impact require supporting measurements or other project evidence. Do not infer outcomes from the existence of documentation alone.
